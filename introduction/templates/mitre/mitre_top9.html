CWE-352: What is Cross Site Request Forgery ?

A online security flaw called cross-site request forgery (CSRF) enables an attacker to trick users into taking actions they did not plan to take. It gives an attacker the ability to partially get around the same origin policy, which is meant to stop various websites from interfering with one another.

A successful CSRF attack involves the attacker tricking the victim user into doing an accidental action. For instance, they might need to do this to make a money transfer, reset their password, or update their email address on file. The attacker might be able to take full control of the user's account depending on the nature of the action. The attacker might be able to fully manage all the data and functionality of the application if the compromised user has a privileged role inside it.

How to protect
  • User django's builtin csrf_token
  • For other framework look for similar method
  • Mark the session cookie SameSite=Lax (or Strict): the browser then refuses to attach it to cross-site requests, so a forged request arrives unauthenticated

Note on SameSite: the lab's auth_cookiee is now set with HttpOnly, Secure and SameSite=Lax, so the browser no longer sends it with a cross-site subresource request - an <img src="...transfer...">, an iframe, a fetch() or an auto-submitted cross-site form gets a logged-out response, and that transfer never happens. Lax still allows a cross-site top-level GET navigation, and the transfer of this badly designed bank is a GET (/mitre/9/lab/api/<recipient>/<amount>), so the attack still works if your payload makes the victim's browser navigate to it (a link they click, a window.location / meta refresh on your page). That is the lesson: SameSite=Lax kills the silent, invisible variants, but only a state-changing request behind POST + a verified CSRF token (or SameSite=Strict) is actually safe.
