CWE-918: Server-Side Request Forgery

The web server receives a URL or similar request from an upstream component and retrieves the contents of this URL, but it does not sufficiently ensure that the request is being sent to the expected destination.
By providing URLs to unexpected hosts or ports, attackers can make it appear that the server is sending the request, possibly bypassing access controls such as firewalls that prevent the attackers from accessing the URLs directly. The server can be used as a proxy to conduct port scanning of hosts in internal networks, use other URLs such as that can access documents on the system (using file://), or use other protocols such as gopher:// or tftp://, which may provide greater control over the contents of requests.


This lab helps you to get an idea of how SSRF can result in major Security flaw. The next pages shows some blog, but can you figure out how the blogs are presented?

This website sends a request to the given url and displays the page withing the page. There is a page at /ssrf_target which only allowes request from localhost ( ie 127.0.0.1 ), and an attacker used to be able to reach it (and any other internal address, such as the cloud metadata service at 169.254.169.254) by making the server fetch it.
The fetch utility is now mitigated: it only accepts http/https URLs whose host is on a positive allow list and resolves to a public address, and it does not follow redirects.
Try it with an allowlisted URL such as https://example.com - the page content is fetched and shown. Then try http://127.0.0.1:8000/ssrf_target, http://[your ip]/ssrf_target, http://169.254.169.254/latest/meta-data/ or file:///etc/passwd: every one of them is rejected before any request is made. Extra hosts can be allowed with the SSRF_ALLOWED_HOSTS environment variable.
